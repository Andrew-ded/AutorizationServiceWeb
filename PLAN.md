# План: сервис авторизации

Документ-первоисточник. Задачи в GitHub Issues ссылаются сюда за контекстом и обоснованием
решений; здесь не дублируется то, что уже описано в [README.md](README.md) (структура решения,
шаблонная обвязка, инструкции по добавлению сущностей).

**Статус:** в разработке. Эпики — issues [#1](../../issues/1), [#2](../../issues/2),
[#3](../../issues/3), [#4](../../issues/4), [#5](../../issues/5).

---

## 1. Зачем

Единая точка выдачи прав для внутренних приложений завода. Сегодня каждое приложение решает,
кому что можно, самостоятельно и по-своему. Нужна одна таблица «пользователь × приложение ×
право», которую ведёт администратор в одном месте, и один способ для приложения узнать, что
пользователю можно.

Ядро — ручная таблица прав (`UserAppGrant`). Всё остальное — обвязка вокруг неё.

---

## 2. Принятые решения

Решения зафиксированы; менять их — отдельное обсуждение, а не правка задачи.

### 2.1. Токены: stateless-проверка, аудит в БД

**Решение.** Токены — подписанные JWT. Потребители валидируют их **локально**, по публичному
ключу из JWKS, не обращаясь к сервису. Каждый **факт выдачи** записывается в БД как
аудит-запись.

**Почему.** Сервис авторизации — единая точка отказа для всего завода. При локальной валидации
его недоступность не останавливает приложения: они продолжают принимать уже выданные токены до
истечения срока. При централизованной проверке падение сервиса означает остановку всех
потребителей сразу.

**Следствия.**
- `Token` — это **журнал выдач**, а не «действующие токены». Поля: `Jti`, `Subject`, `AppId`,
  выданные scopes, `IssuedAt`, `ExpiresAt`, плюс поля отзыва (см. 2.2).
- Записи не удаляются — это аудит. Чистка только по retention (см. 2.6).
- Проверка «активен ли токен» на стороне сервиса **не выполняется**: сервис его не видит.

### 2.2. Отзыв: флаг на записи выдачи + список jti

**Решение.** Отдельной сущности `RevokedToken` **нет**. Отзыв — это флаг на аудит-записи:
`IsRevoked`, `RevokedAt`, `RevokedBy`, `RevokeReason`. Потребители периодически забирают список
jti отозванных и ещё не истёкших токенов и держат его у себя.

**Почему нет отдельной сущности.** Все выданные токены и так лежат в `Token`. Вторая таблица
хранила бы подмножество первой и требовала бы их синхронизации — лишний источник расхождений.

**Массовый отзыв работает бесплатно.** Поскольку журнал содержит `Subject` и `ExpiresAt`, отзыв
«сотрудник уволился» — это одно обновление:

```sql
UPDATE Tokens SET IsRevoked = 1, RevokedAt = @now, RevokeReason = @reason
WHERE Subject = @subject AND ExpiresAt > @now AND IsRevoked = 0
```

Это закрывает сценарий, ради которого обычно заводят отзыв по `subject + timestamp`, — точечный
отзыв по jti остаётся для случая «конкретный токен утёк».

**Окно отзыва.** Отзыв не мгновенный: он вступает в силу не позже, чем через интервал опроса
списка потребителем. Интервал и TTL токена задают это окно — см. 2.5.

### 2.3. Подпись: RS256 + JWKS, ротация с первого дня

**Решение.** Подпись RS256. Публичные ключи отдаются через `/.well-known/jwks.json`. В токене —
заголовок `kid`. JWKS отдаёт **массив** ключей, а не один.

**Почему не HMAC (текущее состояние кода).** При HS256 ключ подписи является и ключом проверки,
то есть каждый потребитель должен знать секрет, которым выписываются токены. Любое приложение
получает возможность выпустить токен от имени сервиса. Скомпрометированный потребитель = полная
компрометация. При RS256 потребители получают только публичный ключ.

**Почему массив ключей сразу.** JWKS — это набор именно ради ротации: ввели новый ключ →
потребители подхватили → перевели подпись на него → старый выключили. С единственным ключом
любая ротация (плановая или после компрометации) одномоментно ломает всех потребителей.
Разделяем: «текущий ключ подписи» и «ключи, принимаемые при проверке».

**Хранение приватного ключа.** Сертификат в машинном хранилище Windows (`LocalMachine\My`),
ключ помечен non-exportable, доступ по отпечатку, ACL на учётную запись пула приложений.
Не файл на диске и не значение в `appsettings.json`. Это также снимает вопрос «что делать с
ключом в git» — его там нет.

### 2.4. `check-access` не реализуется

**Решение.** Эндпоинта проверки прав на стороне сервиса не будет. Права (scopes) находятся
внутри токена, потребитель читает их после локальной проверки подписи.

**Почему.** Он противоречит 2.1: если потребитель уже проверяет подпись локально и видит scopes
в токене, поход в сервис за тем же ответом возвращает единую точку отказа, которую 2.1 как раз
убирает, — и добавляет требования к доступности и нагрузке.

**Про клиентов на .NET Framework 4.7.** Отсутствие `check-access` их не отсекает: пакет
`System.IdentityModel.Tokens.Jwt` поддерживает net461+, то есть локальная валидация им доступна
тем же кодом. Отдельный путь для старых клиентов не нужен.

Задача [#20](../../issues/20) закрыта по этому решению.

### 2.5. Время жизни и audience задаёт сервис, а не клиент

**Решение.** `ExpiresInMinutes` и `Audience` **не принимаются от вызывающего**. TTL берётся из
политики приложения (`App`), audience выводится из приложения и запрошенных scopes. Запрос может
попросить срок **меньше** максимума; больше — отклоняется.

**Почему.** Сейчас (`Application/Services/JwtService.cs`, запись `CreateJwtTokenRequest`) оба
поля приходят из запроса. Это значит, что клиент назначает себе срок жизни токена и выбирает,
для какого сервиса токен будет принят: можно попросить год и чужой audience. Для сервиса
авторизации это дыра, а не гибкость.

`JwtOptions.AccessTokenMinutes` становится **верхней границей по умолчанию** для приложений,
у которых своя политика не задана.

### 2.6. Эксплуатация — часть плана, а не «потом»

Аудит изменения прав (кто, кому, когда выдал или снял), ротация ключей, retention журналов и
логов, бэкап, мониторинг. Для системы, выдающей доступы, это функциональные требования: ошибка
здесь не проявляется падением, она тихо выдаёт лишнее. Эпик [#46](../../issues/46).

### 2.7. Тесты

Интеграционные тесты на выдачу, проверку и отзыв — через `WebApplicationFactory` поверх
InMemory-провайдера. Инфраструктура для этого уже есть: `AddInfrastructure(configuration,
useTestDb)` переключает провайдер (`Infrastructure/Extensions/ServiceCollectionExtensions.cs`).
Эпик [#45](../../issues/45).

## 3. Модель данных

```
ADUser ──┐
         ├── UserAppGrant (ADUserId, AppId, ScopeId)   ← ядро: ручная таблица прав
App ─────┤                 unique(ADUserId, AppId, ScopeId)
         │
         └── Scope (AppId, Name)                        ← права принадлежат приложению

App: Id, Gid, Name, Description, ClientId, ClientSecretHash, TokenLifetimeMinutes
Token (журнал выдач): Id, Jti, Subject, AppId, Scopes, IssuedAt, ExpiresAt,
                      IsRevoked, RevokedAt, RevokedBy, RevokeReason
MobileUser: Id, Username, CodeHash, ADUserId
```

### Что меняется в текущем коде

| Сейчас | Нужно | Почему |
|---|---|---|
| `Token` с `IsActive`, навигациями на `Claims`/`Scopes`/`App` | Журнал выдач: `Jti`, `Subject`, `AppId`, scopes строкой, `IssuedAt`, `ExpiresAt`, поля отзыва | При stateless-проверке «действующий токен» в БД никто не читает (2.1) |
| Сущность `Claim` (`Key`/`Value`, глобальная, без владельца) | Удалить | Ни к чему не привязана; произвольные claims в токене задаёт выдающий код, отдельная таблица-справочник не нужна. Плюс имя конфликтует с `System.Security.Claims.Claim` |
| `Scope.App`, `Token.App` — навигации без FK | Явные `AppId` + навигация | Иначе EF создаёт shadow-property, по которой нельзя строить запросы и индексы |
| `App.Gid` (Guid) **и** `App.Id` (int) | Один идентификатор наружу — `Gid`; `Id` остаётся внутренним ключом. В токене `app_id` = `Gid`. Все внешние ссылки и API — по `Gid` | Сейчас `JwtService` кладёт в токен `Gid`, а связи ссылаются на `Id`; при join непонятно, что с чем сопоставлять |
| `MobileUser.Code` открытым текстом | `CodeHash` | Если код — секрет привязки, он не может лежать в открытом виде |

Правило: у каждой связи — **явный внешний ключ**, у `UserAppGrant` — составной уникальный
индекс, иначе одно и то же право назначится дважды.

## 4. Потоки

### 4.1. Пользователь из домена → токен

```
Клиент → (Negotiate, доменное рукопожатие) → сервис
       ← Bearer JWT (sub=пользователь, scopes из UserAppGrant, kid, jti)
Клиент → потребитель, с Bearer
                     потребитель валидирует подпись по JWKS локально,
                     сверяет jti со списком отозванных, читает scopes
```

Отдельной формы входа с паролем не требуется — пользователь уже аутентифицирован доменом.
Из этого следует, что макет `Вход - Auth Admin.html` (логин/пароль) для админки **не нужен**,
см. 5.2.

### 4.2. Приложение → токен (client credentials)

```
Приложение → POST /api/v1/token (client_id + client_secret)
           ← Bearer JWT (sub=приложение, scopes приложения)
```

TTL и audience — из политики `App` (2.5), не из запроса.

### 4.3. Отзыв

```
Администратор → отзыв в админке → Token.IsRevoked = true
Потребитель   → периодический опрос списка отозванных jti (REST, #19)
              → позже: gRPC-стрим (#36, отложено до решения по хостингу)
```

## 5. Что известно про реализацию

### 5.1. Инфраструктурные правки, которые надо сделать до фич

- **Логирование тел ответов.** `Web/Middleware/RequestLoggingMiddleware.cs` подключён **до**
  `UseAuthentication` и на уровне Debug пишет тела ответов целиком — то есть выданные JWT
  попадают в лог-файл. Заголовок `Authorization` маскируется, тело ответа — нет. Нужно исключить
  из логирования тела ответов эндпоинтов выдачи токенов.
- **Транзакции.** `Infrastructure/Repository/GenericRepository.cs` вызывает `SaveChangesAsync` в
  каждом методе. Назначение пользователю нескольких прав одним действием даст несколько
  независимых коммитов вместо одного. Нужен UnitOfWork либо вынесение `SaveChanges` из
  репозитория.
- **Запросы со связями.** `IRepository<T>` умеет только «дай всё» — для `UserAppGrant` с join на
  три таблицы это не работает. Специализированные запросы пишутся в handler'ах, generic-репозиторий
  для них не расширяется.
- **Валидация конфигурации.** `Program.cs` читает `JwtOptions` через `.Get<JwtOptions>()` в обход
  `ValidateOnStart` — схема аутентификации настраивается на непровалидированном значении.
- **Логи по папкам.** `Logs/{date}/{time}/` создаёт новую папку **на каждый запуск**; на IIS с
  рециклингом пула это сотни папок, и нет `retainedFileCountLimit` — диск не чистится.
- **Мусор от шаблона:** `Web/Controllers/SampleController.cs`,
  `Application/Features/ADUser/Queries/GetAllSamplesQuery.cs`, закомментированные `DbSet` в
  `AppDbContext`, пустая папка `Features/ADUser/Command` в `Application.csproj`.

### 5.2. Админка: макет — не вёрстка

`Auth Admin - обновлено.html` (370 КБ) — **экспорт из дизайн-инструмента**, а не разметка:
React 18 UMD с CDN, `<script type="__bundler/manifest">`, содержимое в виде вызовов
`React.createElement` внутри экранированной строки. Переиспользовать её нельзя.

Из этого следует:
- задача [#25](../../issues/25) — это **написание вёрстки по макету как по картинке**, а не
  «нарезка». Оценка соответствующая;
- CDN-скрипты за периметром завода могут не загрузиться — всё, что нужно странице, кладём в
  `wwwroot`;
- `Вход - Auth Admin.html` не реализуется: админка под доменной аутентификацией (4.1).

## 8. Что считается сделанным

Задача закрывается, когда выполнены критерии приёмки **в её теле**. Отдельного этапа проверки
в конце нет — это была ошибка прежней структуры (эпик «Верификация» собирал критерии приёмки
всех остальных эпиков в отдельный список, который по построению закрывался последним и потому
ничего не проверял).

Общие требования ко всем задачам с кодом:
- `dotnet build` без ошибок и новых предупреждений;
- изменения схемы сопровождаются миграцией, применённой и на InMemory, и на SQL Server;
- новое поведение покрыто тестом (эпик [#45](../../issues/45));
- секреты не попадают ни в репозиторий, ни в логи.
